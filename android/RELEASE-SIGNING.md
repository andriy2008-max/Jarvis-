# JARVIS 0.1.8 — постійний підпис і оновлення APK

## Принцип оновлень

Стабільний застосунок має незмінний Android package ID `com.andriy.jarvis.stable`, той самий приватний ключ підпису в кожній версії та зростаючий `versionCode` (у 0.1.8 — 18). Новий APK із таким самим ID та сертифікатом оновлює наявний застосунок, замість створення нової іконки. Жоден тимчасово підписаний Preview не повинен поширюватися як оновлення користувача.

**Одноразовий перехід:** попередні тестові копії `com.andriy.jarvis`, `com.andriy.jarvis.preview` та `com.andriy.jarvis.preview17` не можуть автоматично перетворитися на stable: Android забороняє оновлення між різними package ID або сертифікатами. Перед очищенням старих копій збережи нотатки; потім встанови stable один раз. Надалі оновлення відбуватимуться поверх stable.

## Приватний комплект ключів

Підготовлено користувацький PKCS12 keystore `jarvis-stable.jks` (RSA 3072, alias `jarvis-stable`) разом із паролями та base64-записом keystore. Зберігай приватний комплект на своєму телефоні або в захищеній резервній копії. **У репозиторії є лише публічний SHA-256 сертифіката**, а не сам keystore або паролі. GitHub Actions перевіряє, що кожен stable APK підписаний сертифікатом із `android/RELEASE-CERT-SHA256.txt`; якщо сертифікат інший, збірка завершується помилкою.

## Налаштувати GitHub Secrets через телефон

Відкрий <https://github.com/andriy2008-max/Jarvis-/settings/secrets/actions> → **New repository secret**. По черзі додай чотири секрети з файлів приватного комплекту (назва дорівнює імені файлу без `.txt`; значення — вміст файла):

1. `JARVIS_SIGNING_KEYSTORE_BASE64` — повний однорядковий base64 з приватного комплекту.
2. `JARVIS_RELEASE_STORE_PASSWORD` — пароль сховища ключів.
3. `JARVIS_RELEASE_KEY_ALIAS` — `jarvis-stable`.
4. `JARVIS_RELEASE_KEY_PASSWORD` — пароль приватного ключа.

Не вставляй приватні значення в розмову, в коміти, Pull Request, GitHub Issues, Variables або журнал збірки. Їх можна додавати **лише** в GitHub Actions **Secrets**. GitHub не показує значення збереженого секрету для повторного копіювання, тож резервна копія обов'язкова.

## Збірка після налаштування

GitHub → Actions → **Android APK (Jarvis)** → **Run workflow** → branch `main` → `variant=stable`. Workflow навмисно запускається **лише вручну**. Він перевіряє 6 тестових класів команд, двічі компілює APK, перевіряє Android package ID, `versionCode`, підпис і pinned SHA-256 сертифіката. Якщо ключі не додано, stable збірка завершується з помилкою, а не створює непридатний APK.

Успішний результат публікується у GitHub Releases як `JARVIS-0.1.8-stable.apk`, з прямим посиланням для Android. Версію `v0.1.8` дозволено опублікувати тільки один раз. Для наступних оновлень збільшуй `versionCode`, оновлюй `versionName` і тег GitHub Release, але **ніколи не змінюй keystore, certificate SHA-256 чи package ID**.

## Відновлення

Якщо загубити keystore, який створив першу stable-версію, оновлення без зміни package ID буде неможливим. Тому приватний архів зі сховищем, паролями і резервною копією слід зберігати як довгостроковий актив. Його не можна викладати у відкритий доступ.

## Випуск 0.1.9

Для наступного Stable APK версія `0.1.9`, `versionCode=19`. Зберігаються незмінними `com.andriy.jarvis.stable` і закріплений публічний відбиток сертифіката з `android/RELEASE-CERT-SHA256.txt`. Ключ зберігається тільки в GitHub Secrets. Збірка/публікація залишаються ручними, без автоматичного випуску після цього коміту.

## Випуск 0.1.10

`versionCode=20`, `versionName=0.1.10`, той самий пакет `com.andriy.jarvis.stable` та закріплений SHA-256 підпису. Цей випуск не слід видавати як Preview, щоб уникнути дублювання іконок. Збірка та реліз здійснюються окремо лише після явної команди.
