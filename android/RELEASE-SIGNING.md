# JARVIS 0.1.5 — постійний підпис і безпечні оновлення

## Поточний стан

У репозиторії **немає приватного ключа** й **немає збережених паролів**. Налаштовано тільки код для роботи з постійним ключем. Для першого stable APK потрібно створити власний довгостроковий ключ і додати його в GitHub Actions Secrets. **Жодна збірка не запускається автоматично.**

| Варіант | Ідентифікатор | Підпис | Оновлення |
| --- | --- | --- | --- |
| `preview` (`assembleDebug`) | `com.andriy.jarvis.preview` | Тимчасовий debug-ключ | Збірки в різних GitHub runners **можуть не оновлювати одна одну** |
| `stable` (`assembleRelease`) | `com.andriy.jarvis.stable` | Один довгостроковий користувацький ключ | Майбутні stable APK оновлюють попередній stable APK, якщо сертифікат той самий, а `versionCode` збільшено |

Обрано окремий `com.andriy.jarvis.stable`, щоб **перша** стабільна версія встановилася поряд зі старим `com.andriy.jarvis` та Preview, не вимагаючи видалення та не знищуючи їхні нотатки. Нотатки між різними пакетами **не переносяться автоматично**. Після переходу на stable необхідно використовувати **той самий** keystore для кожного оновлення.

## 1. Створити ключ ОДИН РАЗ на власному ПК

Потрібен JDK `keytool`. Приклад:

```sh
keytool -genkeypair -v -keystore jarvis-stable.jks -alias jarvis-stable -keyalg RSA -keysize 3072 -validity 10000 -storetype PKCS12
```

Вибери довгий пароль, збережи `jarvis-stable.jks` і пароль **поза GitHub** в захищеному резервному місці. Не надсилай `.jks`, пароль чи base64 у ChatGPT, коміти або повідомлення. Втрата ключа унеможливить штатне оновлення підписаних ним APK. **Не використовуй ключ із попередніх тимчасових debug-збірок.**

## 2. Додати GitHub Secrets (лише через налаштування репозиторію)

GitHub → `andriy2008-max/Jarvis-` → Settings → Secrets and variables → Actions → New repository secret:

- `JARVIS_SIGNING_KEYSTORE_BASE64` — base64-кодування байтів `jarvis-stable.jks` в один рядок. У PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("jarvis-stable.jks"))`.
- `JARVIS_RELEASE_STORE_PASSWORD` — пароль keystore.
- `JARVIS_RELEASE_KEY_ALIAS` — `jarvis-stable` (якщо саме такий alias обрано).
- `JARVIS_RELEASE_KEY_PASSWORD` — пароль приватного ключа (для PKCS12 зазвичай той самий, що й пароль keystore).

**Секрети ще не налаштовані цим комітом.** Не публікуй їх у відкритому репозиторії. Використовуй збережену копію ключа для всіх наступних релізів.

## 3. Ручна збірка — тільки за окремою командою

GitHub → Actions → **Android APK (Jarvis)** → **Run workflow** → `main` → `variant=stable`. Якщо хоч один секрет відсутній — збірка `stable` припиняється **до компіляції**. Debug Preview збирається з `variant=preview` і не використовує release-ключ. Після успішної збірки завантаж артефакт із GitHub Actions. У workflow свідомо **немає автопублікації в Releases**: попередні запуски отримували 403 і не створювали релізу.

Сценарій перевіряє Java-парсери, двічі збирає вибраний варіант, перевіряє цифровий підпис `apksigner`, точні `applicationId`, `versionCode=15`, `versionName=0.1.5` і SHA-256.

## 4. Подальші оновлення

Під час створення версії 0.1.6 збільшити `versionCode` щонайменше до 16, `versionName` до `0.1.6`, залишити `com.andriy.jarvis.stable` та підписувати тим самим сертифікатом. **Не перестворюй keystore**. Якщо зміниться пакет або сертифікат, Android не вважатиме APK оновленням; дані не перенесуться автоматично.

## Обмеження

- Це підготовлена інфраструктура, не створений реліз: без секретів підписаний APK ще не можна отримати.
- Preview 0.1.4 підписаний іншим debug-ключем, тому Preview 0.1.5 може не встановитися поверх нього; не видаляй стару програму без резервної копії нотаток.
- Release-підпис — це не Google Play App Signing, а ключ власника, тому збереження резервної копії критично важливе.
